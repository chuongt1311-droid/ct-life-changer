# Future-Date Editing (Sub-project B) — Design

**Status:** approved (brainstormed 2026-09-15, following sub-project A —
`docs/superpowers/specs/2026-09-15-flexible-schedule-editing-design.md`, shipped).

## Problem

A only reshapes *today*. CT often knows about a conflict days ahead — a
dentist appointment next Thursday, a trip that wipes out Tuesday's gym slot —
and today the only way to act on that is to wait until the day arrives and
either hand-edit it then or let the guard reflow it. Weekday **templates**
already have full hand-editing (`/templates`), but a template edit is
permanent and recurring; it can't say "just this one Thursday."

Plans, however, don't exist ahead of time. `ensureTodayPlan` builds today's
plan from its template the first time today is loaded; `generateTomorrowPlan`
builds tomorrow's plan from its template the evening before, once, and does
nothing if a plan row already exists. Nothing builds a plan for the day
after tomorrow until *its* evening arrives. So "editing a future date" first
has to answer: edit *what*, when nothing exists yet to edit?

## Scope

**In scope:**
- A **Plan ahead** page listing the next 14 days (today and tomorrow
  excluded — those are Today's and Day-changed's job).
- Opening a date builds an on-the-spot **preview**: if a plan row already
  exists for it (e.g. tomorrow, generated by tonight's evening check-in),
  load its real blocks; if not, build one from its weekday template using
  the same guard/adjustment pipeline `ensureTodayPlan` already uses.
- Editing that preview with move / resize / drop / add — the exact same
  vocabulary and `applyEdits` pipeline from sub-project A, stacked and
  reviewed as one diff before saving.
- Saving persists a real `plans` + `blocks` row for that date, marked
  `overridden: true`. Because `ensureTodayPlan` and `generateTomorrowPlan`
  both skip generation once a plan row exists for a date, the saved
  override is never regenerated or clobbered when that day's automatic
  generation would otherwise have run.

**Out of scope:**
- Any date beyond 14 days out, or before today (history is already
  read-only and stays that way).
- Re-checking a saved future override against the guard's state as that day
  actually arrives. CT chose "it sticks as-is" — once saved, an override
  behaves exactly like a template edit or a confirmed Today edit: it wins,
  full stop. If CT's real state has drifted enough by then to matter, the
  existing Day-changed reflow flow (sub-project A) is still there that
  morning to reshape it further, same as it would for an unedited day.
- Editing a date that's already in the past, or one whose plan is already
  underway (that's Today/A's job, not this page's).
- Mentor tool use — that's sub-project C, which *calls into* the functions
  this spec builds (`previewFuturePlan`, `confirmFuturePlan`) rather than
  duplicating them.

## Design

### Data: no schema change

`plans.overridden` already exists (`src/lib/db/schemas.ts:77`) and already
means exactly "CT deliberately set this, not the guard" — `reassessMorning`
sets it today or hand-editing to true after a morning override, and the
mentor's context already reads it (`src/lib/mentor/assembleContext.ts:52`,
`src/core/mentor/context.ts:71`, `"CT overrode them: yes/no"`). Setting it
when a future-date plan is first saved reuses that meaning correctly: the
mentor will see the truth for that day without any prompt changes.
`blocks` needs no change either — a block's `date` column already ties it
to any date, not just today.

### `previewFuturePlan(client, date, now): Promise<{ plan: DayPlan; source: 'existing' | 'generated' }>`

New function, `src/lib/planner/planAhead.ts`. Loads settings; checks
`repos.plans.get(date, 'date')`:
- **Exists** → load its blocks the same way `previewEdits` already does
  (`rowToBlock` over `repos.blocks.list({ date })`), return
  `{ plan, source: 'existing' }`.
- **Doesn't exist** → load the weekday's template
  (`repos.templates.get(weekdayOf(date))`; throw if genuinely missing, same
  contract `ensureTodayPlan` already has for onboarding-incomplete states),
  run the guard against the CT's most recent 7 days of history (the only
  history there is — this is a best-effort preview, not a prophecy; noted
  once in this doc rather than re-litigated per-task) via `assess`, then
  `buildDay(template, date, settings, assessment.adjustments)`. Return
  `{ plan, source: 'generated' }`. **This does not write anything** —
  identical contract to `previewEdits`.

`source` lets the UI show "This is a generated preview, not a saved plan
yet" vs "This is what's already planned" — the one honest difference CT
should see before editing.

### `previewFutureEdits(client, date, edits, now)`

Thin composition: call `previewFuturePlan` to get the base plan (whichever
source), then run the exact same `validateEdits` → `applyEdits` sequence
`previewEdits` already runs, over that base plan instead of one loaded
straight from `blocks`. Return shape matches `previewEdits`'s:
`{ plan, diff, conflicts, errors }`.

### `confirmFuturePlan(client, ownerId, date, plan): Promise<void>`

Persists `plan.blocks` via the same `blockToRow`/`repos.blocks.upsert`
sequence `confirmReflow` already uses, **and** upserts the `plans` row
itself (which `confirmReflow` never needed to, since Today's plan row
already exists by the time CT edits it): `state` and `adjustments` come
from whatever `previewFuturePlan` last computed for that date (passed
through, not recomputed), `overridden: true`.

### UI: `/plan-ahead`

New page, following the `/templates` pattern (own route, own actions file,
signed-in gate via `isOwner`). Two states, same shape as
`TemplateEditor.tsx`'s list/detail split:

- **List:** the next 14 dates, weekday name + short date, a hint per row
  ("planned" if a plan row exists, "from template" if it would be
  generated). Tapping a row opens it.
- **Detail:** reuses `EditableDay`'s tap-row → `EditBlockSheet` → stack →
  `DiffList` → confirm flow verbatim, parameterized by the chosen date
  instead of always "today." `EditableDay` already takes `blocks` and
  `actions` as props and calls `previewEditsAction`/`confirmEditsAction`
  internally — those two server actions become thin wrappers that also
  accept an explicit `date`, delegating to `previewFutureEdits`/
  `confirmFuturePlan` when it isn't today. No `ThumbBar`/"Start rest"
  action here — that's Today's business, not this page's; the passed-in
  `actions` slot is just a "Save" button labeled from `source` ("Save this
  day" vs "Save override").

### Testing

- `planAhead.test.ts`: `previewFuturePlan` returns `source: 'existing'`
  when a plan row is present; returns `source: 'generated'` from the
  template when it isn't; throws when the weekday has no template.
- `previewFutureEdits`/`confirmFuturePlan`: reuse the `fakeClient` pattern
  from `reflowDay.test.ts`; assert `confirmFuturePlan` sets
  `overridden: true` and that a subsequent `ensureTodayPlan`-style "does a
  plan already exist" check would see the row (i.e. don't regenerate over
  it).
- E2E: opening `/plan-ahead`, picking a date with no existing plan,
  editing one block, confirming, and re-opening the same date shows the
  edited block persisted (not regenerated back to the template).

## Self-review

1. **Spec coverage:** every requirement from the brainstorm (14-day range,
   generate-on-demand preview, edit via A's vocabulary, sticks-as-is
   staleness policy, own page) is covered above.
2. **Placeholder scan:** none.
3. **Consistency:** `confirmFuturePlan`'s state/adjustments come from the
   preview, not recomputed at confirm time — otherwise a slow CT (preview
   now, confirm five minutes later) could save adjustments computed against
   a state that's already stale by the time they hit Save, which is a
   sillier kind of staleness than the one CT explicitly said not to guard
   against. Fixed by threading the value through instead of recomputing.
4. **Ambiguity check:** "next 14 days" is calendar days from `planClock`'s
   `planDate` (today), days 3–16 inclusive (1 and 2 are today/tomorrow,
   already excluded) — stated explicitly rather than left to interpretation
   of "next."
